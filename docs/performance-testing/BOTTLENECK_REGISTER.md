## Current measured evidence (not a capacity certification)

- Post-fix smoke: 93 requests, zero failures; `--run-time limit reached`; Locust exit code 0. Report: `performance/results/smoke-20261020-053853.html`; CSV prefix: `performance/results/smoke-20261020-053853`. The small sample is only a smoke/failure check.
- Successful baseline: 2,341 requests, zero failures, reported 7.81 req/s; five users, spawn rate 1/s, five minutes configured. Aggregated median 18 ms, p95 210 ms, p99 230 ms. The aggregate upper percentiles include login latency and should not replace per-endpoint percentiles.
- Completed load: 23,352 requests, zero failures, reported 38.95 req/s; 25 users, spawn rate 5/s, ten minutes. The output includes `--run-time limit reached` and exit code 0. Aggregated median/p95/p99 20/260/280 ms. Report: `performance/results/load-20261020-054148.html`; CSV prefix: `performance/results/load-20261020-054148`.
- Login latency: baseline p95/p99 240/250 ms; completed load p95/p99 300/340 ms. This is a real measured increase under the higher-concurrency configuration, but the cause is not established.
- Database benchmark: five samples per query group, all with `error=None`. Mean / p95: `customers_count` 1.105 / 3.614 ms; `audit_logs_count` 0.863 / 2.579 ms; `customer_status_history_count` 0.838 / 2.723 ms; `customers_latest_100` 0.590 / 1.450 ms. These limited read-only queries do not rule out broader DB constraints.
- Docker resource capture: a CSV was recorded during the baseline, but its exact path and numeric measurements must be inserted/reviewed before claiming correlation with latency.
- No agreed p95/p99, throughput, or error-rate service-level objectives were supplied. Define guardrails with the platform owner before capacity sign-off.

## Investigation checklist

- [ ] Reproduce with the smallest concurrency that exhibits the issue.
- [ ] Compare with baseline using the same environment, data, and configuration.
- [x] Run `-Profile load` through the configured ten-minute duration; output showed `--run-time limit reached`, exit code 0, zero request failures, and HTML/CSV report paths.
- [ ] Review per-endpoint HTTP failures/timeouts and p95/p99, rather than relying only on aggregate response percentiles.
- [ ] Correlate Docker stats timestamps with response-time outliers; record backend replica CPU, memory, restarts, network I/O and block I/O.
- [ ] Check PostgreSQL active connections, pool exhaustion, slow queries, locks, indexes and I/O where appropriate.
- [ ] Check report/document worker queues and storage I/O only when those write-producing workloads are deliberately enabled.
- [ ] Check AI provider latency, quotas, concurrency and cost only during separately approved AI feature tests.
- [ ] State evidence separately from hypothesis.
- [ ] Re-run the original profile after each fix and archive both reports.

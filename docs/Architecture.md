# FinPilot architecture

## 1. System overview

FinPilot is implemented as a backend-first REST platform. The canonical Python application is in `backend/app/`; it uses FastAPI for HTTP routing, Pydantic for request/response validation, SQLAlchemy for persistence and PostgreSQL as the primary relational database. Alembic controls schema changes. pgvector supports vector-backed retrieval features.

At runtime, the API can be deployed behind HAProxy and alongside separate worker processes. Docker Compose provides the local development environment. The release deployment configuration is maintained under `deploy/`.

## 2. Logical request path

```text
HTTP client
    |
    v
HAProxy (Compose / deployment entry point)
    |
    v
FastAPI application
    |
    +-- Middleware: request/security controls, request IDs, tenant context
    |
    +-- API router: authentication and dependency validation
             |
             v
         Service layer
             |
             v
         Repository layer
             |
             v
         SQLAlchemy models/session
             |
             v
         PostgreSQL
```

Business services coordinate validation, access rules, transactions and domain behavior. Repositories encapsulate query/persistence operations. API routes should remain thin and should not become a second implementation of business logic.

## 4. Tenancy and authorization

Business data is partitioned by tenant. The authenticated user and trusted request/session context supply tenant identity; repositories and services must scope reads and writes to that tenant. A caller must not be trusted to choose an arbitrary tenant by submitting an ID in the request.

Some platform-level operations intentionally inspect more than one tenant. Those paths require trusted platform-admin context and should use explicit, documented tenant-filter bypasses with a reason and narrowly scoped target data. A business role label alone must not grant cross-tenant access.

Review nested resources and write operations as well as list endpoints: customer documents, verification records, tasks, feedback history, ticket attachments and similar child records must not be reachable by knowing a UUID from another tenant. Where appropriate, composite foreign keys enforce parent/child tenant consistency in the database.

See [Database Standards](DatabaseStandards.md) and [Known Limitations](KNOWN_LIMITATIONS.md).

## 5. Persistence and migrations

PostgreSQL is the authoritative relational store. SQLAlchemy sessions are injected into requests. Schema changes are represented by Alembic revision files and are applied with `uv run alembic upgrade head` from `backend/` or through the Docker backend container.

The migration history includes pgvector extension usage; the PostgreSQL server must have the extension installed. Review new autogenerated migrations manually and inspect the head graph before merging.

## 6. Provider adapters

AI, OCR, extraction, verification, communication and storage behavior is abstracted behind provider/service boundaries. The example environment chooses mock providers for several integrations. The mock path enables local feature exploration but must not be confused with an external provider having been configured and acceptance-tested.

## 7. Background processing

The Compose configuration defines separate worker services for:

- `app.jobs.sla_monitor`
- `app.jobs.analytics_aggregator`
- `app.jobs.report_export_worker`
- `app.jobs.webhook_delivery_worker`

The API request path should not run long-running report or scheduled work synchronously when a background processing path is defined. Operations teams need health monitoring, worker supervision, failure/retry alerts and duplicate-execution safeguards.

## 8. Local runtime topology

The default development Compose file includes three backend API containers and HAProxy, PostgreSQL using `pgvector/pgvector:pg17`, pgAdmin, four worker services, Prometheus and Blackbox Exporter. HAProxy exposes the primary local API on port 8000; PostgreSQL is bound to host port 5433; metrics/admin services have separate local ports.

Multiple API containers on a single developer host do not provide host-level availability. Production topology must provide independent failure domains and a database/storage resilience strategy.

## 9. API composition

The router imports and include operations are centralized in `backend/app/main.py`. The API is versioned under `/api/v1`. FastAPI generates:
- `/docs` — Swagger UI.
- `/redoc` — ReDoc.
- `/openapi.json` — machine-readable OpenAPI schema.

For endpoint truth, inspect the running version's OpenAPI schema and implementation, not an old exported spec or static README table.

## 10. Design review questions

When adding a feature, verify:

1. Which tenant owns the resource and how tenant context is established.
2. Which roles may read, create, change, delete or approve it.
3. Whether service logic and repository query scope are consistent.
4. Whether history/audit events are recorded where required.
5. Whether transactions avoid partial writes or leaked files.
6. Whether migrations support existing data and safe rollback.
7. Whether tests cover success, invalid input, unauthorized access, cross-tenant access and failure paths.
8. Whether any external side effect is idempotent, retried and observable.
